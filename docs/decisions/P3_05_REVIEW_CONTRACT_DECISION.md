# P3-05A 試遊候補と手動評価の決定

日付: 2026年7月27日

## 決定

1. P3-03Rの66構造を、自動条件だけで公式問題へ昇格しない。
2. 66構造すべてをP3-05の試遊母集団として固定する。
3. 各テンプレートへ`p3-05-review-v1:<templateId>`の固定seedを使う。
4. `templateId`を明示して生成し、seedのhash衝突やprofile選択による別候補への置換を防ぐ。
5. レビューIDへ`templateId`と`boardHash`先頭12桁を含める。
6. 盤面内容が変わった場合、古いレビューID、手動評価、採用判断を使い回さない。
7. 候補証拠と手動試遊記録を別データとして保存する。
8. 候補証拠には盤面データ、厳密最短、代表解法、版、hash、自動品質指標を含める。
9. 手動試遊記録には試遊者、端末、ブラウザ、日時、試行、クリア、評価、既知の詰み方、判断理由を含める。
10. `accept`には少なくとも1回のクリアと5項目すべての評価を必要とする。
11. 人が記録したベスト操作数が厳密最短を下回る場合、不整合として拒否する。
12. P3-05の正式問題集確定条件は、完了した`accept`記録が30件以上であることを最低条件とする。
13. 30件以上という数だけで採用せず、profile配分と問題の似すぎもP3-05Cで確認する。
14. P3-05Aでは公開ゲームやCodebergへ候補を接続しない。
15. P3-05Aでは手動試遊を実施済みと記録しない。

## 理由

- 自動検査は厳密最短、初期直行、構造重複を確認できるが、面白さ、説明の分かりやすさ、操作時の納得感までは確定できない。
- 生成器や盤面内容が変わった後に古い評価を引き継ぐと、評価対象が別物になる。
- 端末とブラウザを記録しないと、操作のしづらさが盤面由来か環境由来か判断できない。
- 厳密最短より少ない手数の人間記録は理論上成立しないため、黙ってランキングや採用証拠へ入れてはいけない。
- JSONとCSVを両方用意すると、機械検査とスマートフォンでの表編集を分けられる。

## 評価項目

```text
enjoyment: 遊んで面白いか
clarity: 状況と次の操作を理解できるか
difficulty: 難しさが適切か
distinctiveness: 他候補と違う考え方が必要か
fairness: 失敗理由に納得できるか
```

各項目は1〜5の整数とする。

## 完了の意味

P3-05A完了は、試遊に必要な候補と記録形式がそろったことを意味する。

次はまだ含まない。

```text
人間試遊完了
公式採用30問確定
本日の出荷接続
ランキング送信
```
